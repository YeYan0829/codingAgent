# System Vision

本文是 CodeAgent 的产品目标与原则权威来源。当前设计状态、有效实现入口和下一步开放问题见[当前设计上下文](PROJECT_GUIDE.md)。已暂停的逻辑架构仅保留在归档中，不代表当前实施方向。

## 1. Problem

当前 Coding Agent 的主要问题是：

- 用户很难知道 Agent 是否真正理解需求；
- Agent 对 repository 的理解通常是临时的、不可检查的；
- 用户往往只能在 patch / diff 出现后验证 Agent 的理解是否正确；
- 大规模 diff 会给开发者带来较高认知负担；
- 产品设计、技术选型和系统设计经常依赖模型记忆或临时判断，缺少可追踪的外部依据；
- 用户很难知道某个设计为什么被提出、参考了哪些方案、放弃了哪些替代方案。

问题不只是 Agent 能否写出代码，还包括开发者和 Agent 是否拥有足够清晰的共同理解、决策依据和验证手段。

## 2. Product Goal

建立一个支持以下完整开发流程的 Software Engineering Agent Runtime：

```text
Intent → Research → Understand → Design → Review → Execute → Verify
```

系统不仅帮助 Agent 编写和修改代码，也帮助 Agent 与开发者共同完成：

- 产品与技术调研；
- 需求澄清；
- repository understanding；
- 系统设计与 change planning；
- 人工 review、追问和修正；
- 受控代码执行；
- 测试与验证；
- 修改解释与 evaluation。

整个过程中，Agent 对需求、外部资料、项目结构、设计决策和代码修改的理解，应尽可能外化为开发者可以检查、追问、补充、引用和追踪的 artifact。

## 3. Core User Flow

### 3.1 Intent

用户描述一个模糊或明确的开发目标。Agent 提取：

- 用户目标；
- 已知约束；
- 未确认假设；
- 需要进一步调研或澄清的问题。

### 3.2 Research

当任务需要外部知识时，Agent 根据目标形成 research questions，并检索官方文档、技术规范、开源项目、已有产品和相关研究。

Research Artifact 记录：

- 调研问题；
- 来源与证据；
- 候选方案和 trade-offs；
- 已确认事实；
- Agent inference；
- 不确定信息；
- 推荐方案及理由。

用户可以检查、追问或补充调研结果。

### 3.3 Understand

Agent 通过受控的只读能力探索当前 repository，并将代码证据与必要的外部 research 结合，按任务需要向用户解释：

- 相关文件与 symbol；
- 模块职责；
- dependency / call relationships；
- 关键 execution flow / data flow；
- 与当前需求相关的 architecture context；
- 证据、推断和未解决问题。

这些解释应区分代码事实、推断和未解决问题，并能回到相应证据。是否需要把它们持久化为结构化模型，留待后续调研决定。

### 3.4 Design

Agent 基于 Requirement、Research 和当前 repository understanding 形成 Design Preview，包括：

- 对需求的理解；
- 当前系统相关结构；
- 候选实现方案和 rationale；
- 预计影响范围；
- architecture / flow changes；
- 风险和 acceptance criteria；
- 未解决的不确定项。

### 3.5 Review

开发者和 Agent 通过适合当前任务的共享表示在较高抽象级别上交流。具体形态可以是对话、图或其他按需投影，留待后续调研决定。开发者可以：

- 追问模块职责、关系、流程和判断依据；
- 展开文件、symbol 或外部来源等证据；
- 要求进一步解释或比较其他可能方案；
- 补充 Agent 无法从代码直接得知的领域信息；
- 修正错误理解；
- 加入尚未实现的模块或关系，表达候选设计；
- approve、reject 或继续修改 Design。

用户不必先修正 Agent 的项目理解才能继续。追问、解释、补充和提出未来设计都属于正常协作方式。

### 3.6 Execute

Design 被确认后，Agent 才进入受控执行阶段。实际修改在隔离工作区完成，并尽量遵循 approved design。

如果实现中发现设计不可行、需要超出批准范围或无法满足验收标准，系统应记录偏离并重新请求 review，而不是静默改变设计。

### 3.7 Verify

Agent 完成测试和 validation，并输出 Semantic Diff，说明：

- 实际发生了什么变化以及原因；
- design requirement 到 implementation 的映射；
- architecture / flow 的变化；
- 与原 Design 的一致和偏离；
- 测试覆盖及已知限制。

相关 trace、artifact 和 evaluation result 应可追踪。

## 4. Design Principles

### Evidence before assumption

涉及外部事实、技术能力、工具选择和已有方案的关键决策，应尽可能基于可追踪 evidence，而不是模型记忆或未经验证的推断。

### Separate facts from inference

确定性事实、外部证据、用户提供的信息、LLM inference 和未来 proposal 必须尽可能分开。未来设计不能被误报为当前代码事实。

### Plan before execution

默认先理解、调研和设计，再进入 execution。任务规模和风险可以影响流程深度，但不能静默越过必要边界。

### Shared representation

Agent 的项目理解不应只存在于隐藏 context 或长篇自然语言中。应建立开发者和 Agent 都可以引用、检查、追问、补充和修改的共享表示。

### Human-readable intermediate artifacts

Research、Project Understanding、Design、Change Preview 和 Semantic Diff 都应成为明确 artifact，而不是只存在于聊天上下文。

### Traceable decisions

重要决策需要能够回答：

- 为什么这样设计；
- 基于什么事实；
- 参考了什么来源；
- 考虑过哪些替代方案；
- 最终代码是否遵循该决策。

### Evaluation first-class

Evaluation 不是项目完成后补上的 benchmark。可重复的后端能力、表示一致性和人机协作效果应使用适合各自性质的方法验证，不强行压缩成单一分数。

### UI/runtime separation

核心能力属于 Runtime。CLI、Web 或未来 UI 是能力入口和 artifact 投影，不能复制或绕过权限、安全和执行事实。

### Progressive autonomy

Agent autonomy 应根据任务风险和阶段变化。Research 和只读理解可以拥有较高自主性；实际代码修改和高风险操作需要更严格控制。

## 5. Non-goals

当前阶段暂不：

- 做完整 IDE；
- 追求支持所有语言和所有 repository；
- 做 autonomous multi-agent swarm；
- 构建完整 UML suite；
- 自动完成产品经理、架构师和开发者的全部职责；
- 无限制自主浏览 Web 或执行外部操作；
- 追求完全 autonomous software development。

系统首先关注的是：

**让人和 Agent 在软件开发过程中拥有更好的共同理解、决策依据和验证能力。**

## 6. Success Criteria

### Shared Understanding

- Agent 和开发者能够围绕同一个项目理解表示交流；
- 需求、模块、关系、architecture 和 execution flow 可以逐层查看；
- 开发者能够追问依据、补充信息、纠正理解或表达未来设计；
- Agent 能在后续调研、设计和实现中使用正确版本的共享表示。

### Repository Understanding

- 能正确定位需求相关文件和 symbol；
- 能回答 repository architecture 和跨文件关系问题；
- 能预测需求可能影响的组件和代码区域；
- 项目理解中的代码事实可以追溯到 evidence；
- 代码变化后，过时理解不会静默继续作为当前事实。

### Research Quality

- 关键外部事实和技术选择能够追踪到来源；
- Research Artifact 区分 sourced facts、Agent inference 和 unresolved uncertainty；
- 重要技术决策包含 alternative 和明确 trade-off；
- 过时或冲突的信息会被显式标记。

### Design Quality

- Design Preview 明确表达 requirement、affected components、proposed changes、risks 和 acceptance criteria；
- 用户能够在执行前发现并追问 Agent 的错误或不完整理解；
- 当前代码事实与尚未实现的 Proposed Design 保持区分。

### Execution Quality

- 执行阶段不静默偏离 approved design；
- 修改在隔离环境中完成；
- 关键行为存在自动化测试或 validation。

### Explainability

- Semantic Diff 能解释实际修改与原 Design 的一致和偏离；
- 能建立 requirement → design → implementation → validation 的 traceability。

### Evaluation

系统应逐步验证：

- file / symbol localization；
- repository QA；
- change-impact prediction；
- context selection 的相关性和成本；
- design → implementation consistency；
- test / task success；
- 用户能否通过追问找到证据并完成具体项目理解任务；
- 用户补充或提出的设计是否被后续步骤正确使用。
