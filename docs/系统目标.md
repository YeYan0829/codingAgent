# CodeAgent 系统目标

本文件定义当前项目的产品定位、交付范围与成功标准。2026-09-06 起，目标收敛为可公开展示、可安装体验、
可用真实仓库评测验证的本地 Coding Agent。此前围绕 Research Artifact、共享项目理解、Design Preview 和
Semantic Diff 的完整开发流程不属于当前目标，也不作为发布前置条件。

当前事实与展示差距见 [展示导向现状梳理](SHOWCASE_READINESS.md)，实现入口见
[PROJECT_GUIDE](PROJECT_GUIDE.md)，执行顺序见 [NEXT_PHASE_PLAN](NEXT_PHASE_PLAN.md)。本文中的交付标准
是验收目标，不代表所有发布材料已经完成。

## 1. 产品定位

**CodeAgent｜可观测、可干预的本地 Coding Agent**

面向 Linux/WSL2 上的真实 Git 仓库，自主实现从代码检索、读取、修改到受控命令执行和测试验证的 Agent
Runtime，并通过 VS Code 扩展展示会话、工具活动、审批、Diff 和验证结果。开发者能够观察执行事实、拒绝
额外权限、请求停止，并在审阅后采纳或丢弃修改。

“本地”指 Runtime、代码工作区与交互运行在用户环境；GLM/DeepSeek 模型推理调用远程 API。“自主实现”
指执行循环、上下文投影、工具与权限编排、变更交付和产品适配，不指自行训练基础模型或实现 Git、容器引擎。

主要技术：Python、LLM Tool Calling、Git worktree、Linux、Bubblewrap、Docker、SWE-bench、VS Code Extension。

## 2. 核心使用流程

```text
打开 Git 仓库 → 配置模型 → New task → 搜索/读取代码
→ 首次受保护操作审批 → 创建隔离 worktree → 编辑/执行命令/验证
→ 审阅 Diff 与当前验证证据 → Accept 或 Discard
→ 保留 Session 与 worktree，继续后续对话
```

一次用户请求会在本轮模型步骤总预算内自动跨内部执行切片推进，不要求用户反复输入或点击“继续”。达到本轮
上限后保留原 UserTurn、上下文和修改，等待用户明确输入追加步数或新的总上限；Runtime 不会自动扩额。
用户也可以拒绝权限或请求 Stop；Stop 结束当前 UserTurn，后续修正通过新的 UserTurn 发起。重载后可从
History 恢复 Session。当前不承诺任意指令处暂停后原地续跑。

## 3. 四项工程目标

### 3.1 Agent Runtime 与上下文管理

- 自主实现基于 Tool Calling 的观察—行动循环与 ToolRegistry，统一提供搜索、读取、原子编辑、只读 Git
  查询和受控命令执行能力。
- 通过 Session、UserTurn、ModelStep、ToolExchange 组织执行历史；内部切片自动衔接，整轮模型步骤预算由用户
  配置，并且只在达到上限后由用户明确扩额。
- Context Builder 从持久 Event、当前 Runtime Snapshot 与有界工具 Observation 构造请求；按预算缩减旧
  历史，保持工具调用/结果协议完整，最低集合超限时明确终止。
- Session 恢复复检工作区与执行状态，不把旧会话中的描述当作当前文件事实。

不要求独立 Active Code/Working Set、语义压缩、RepoMap/RAG、长期记忆或复杂 Planner。

### 3.2 隔离执行与变更验证

- 用户 source 与 Agent worktree 分离；原子编辑和命令副作用共同推进 Candidate revision。
- 本地产品用 Bubblewrap 执行命令；SWE-bench 用 Docker executor 投影到官方 prepared `/testbed`。
  两者复用 Runtime 边界，但 Docker adapter 不作为通用产品容器工作区宣称。
- 默认限制文件写入与网络访问，额外资源经 Policy/Approval；命令有超时和有界输出。
- Validation Evidence 关联实际命令、revision、tree 与 policy；旧验证不能被当作新修改的当前证据。
- 用户 Accept 时冻结待交付 patch、复检 identity 并三方合并；冲突保留现场，Discard 不覆盖 source。

不承诺 cgroup CPU/内存配额、域名/端口网络 ACL、测试充分性判断或自动合并冲突解决。

### 3.3 可观测与人工干预

- VS Code 展示 UserTurn 时间线、Agent 文本、关键工具调用、命令结果、当前修改和验证状态。
- 展示客观执行状态与需要用户处理的事项，不推测“已理解/已设计”等语义阶段或完成百分比。
- 支持进程内权限审批、cooperative Stop、本轮预算扩额、Session 恢复、原生 Diff 与 Accept/Discard。
- Extension 通过 Product RPC 使用 Runtime，不复制或绕过 ToolRegistry、Policy、Approval 与 Git identity 校验。

不要求 token 级流式输出、运行中直接插入新指令、durable Pause、崩溃后恢复原有进程或自动恢复审批授权。

### 3.4 真实仓库评测

- 使用固定 SWE-bench 任务、官方 prepared image 与 official grader，复用正式 AgentRunner 和上下文逻辑。
- 固定 Runtime commit、selection、provider/model/config、预算和评测环境；保留逐题 patch、执行结果与
  official report，明确区分 Agent 正常结束、当前 validation、非空 patch 与 oracle resolved。
- 以自定义 SWE-bench Verified 50 题子集建立端到端基线，同时报告成本、时延、步骤和失败分类。
- 记录异常 attempt 与恢复操作；不以重复生成后择优的结果充当单次尝试成绩。

目标是提供可检查的真实 Bug Fix 工程证据，不设预期通过率，也不以榜单排名或超过其他 Agent 为交付门槛。
产品审批与交付体验另行验收，不能由无人值守 benchmark 结果替代。

## 5. 完成标准

1. **能看懂：** 首屏及演示能说明用途、核心交互和人工控制边界；架构图能对应到实际模块。
2. **能体验：** 新使用者可按文档在支持环境中安装固定版本，并完成提供的演示任务，不依赖作者工作区路径。
3. **能检查：** 关键状态、命令、审批、修改与验证存在事实依据；展示中的成功/失败可回到记录。
4. **能评测：** 固定 50 题每题都有明确状态，完整报告 oracle、正常结束、validation、成本与失败原因；
   未运行或无法确认的结果明确标记，不补零、不删除困难题、不掩盖恢复尝试。
5. **能解释：** 能从代码与案例说明上下文裁剪、工作区隔离、证据失效、三方合并和 UI/runtime 分离的取舍。

没有高分门槛。中等通过率与完整失败分析也可以构成有效项目证据；性能提升声明需要同条件对照实验。

## 6. 当前非目标

- 原系统目标中的调研产物、共享架构模型、Design Preview、设计审批一致性与 Semantic Diff。
- 完整 IDE、云端协作平台、多人租户、所有操作系统/语言/仓库的兼容。
- Multi-Agent、MCP、长期记忆、通用规划平台和大规模 Context redesign。
- 自动准备所有项目环境、通用 Docker 产品后端、无限制自主网络或主机操作。
- 为简历词条增加没有演示与验证需求的新抽象，或为提高分数反复调整已冻结评测方案。

新增工作优先解决可复现安装、演示体验、结果可信度与可解释性；不要求扩张以上非目标。
