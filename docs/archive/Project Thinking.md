## 1. 我到底想做一个什么东西？

- 我希望它不只是一个会写代码的 coding agent，即：不是只是读代码，改代码，通过测试，跑bug修改的benchmark
- 我希望它能参与软件开发过程中的需求理解、调研、设计、实现和测试
	- 开发者有一个模糊的需求的时候，它是否能够通过恰当的方法（比如挂载相关skill或者进行research）引导其产出规范的需求文档？
	- 符合某一规范的需求文档能否进一步被拆解成功能模块，能否通过调研找到最佳实践，进行竞品分析，能否将调研结果以友好的方式展示给开发者而非一次性吐出大量信息？能否做到决策有依据，参考可溯源？
	- web search结果，project context要如何组织才能让agent有效的利用这些信息进行进一步的系统设计，agent的系统设计怎么展示给开发者，开发者是否可以作为合作者和agent一同进行系统设计，进行审阅和修改？是否要支持图形化的表达方式？
	- 怎么从一份抽象的系统设计落实到代码实现和测试，以及整个流程是否设计的足够灵活，支持做到一半改需求，调研结果已经过时，需要换最佳实践，或者开发者表述模糊等常见软件开发过程中的问题，而非要求用户必须按照设计者预想的流程进行工作
	- agent的每个关键流程，如代码理解能力，人机交互友好度等，是否能够支持后续通过专门的benchmark测试与持续优化，而非只是堆了一堆时髦产品功能和技术栈的一个无法验证的demo
- 我希望开发者能够知道 Agent 是怎么理解项目和需求的

### 我的描述

### 如果只能用一句话描述
这是一个software engineering agent，旨在优化ai辅助开发过程中人机交互的体验，agent如何更好理解代码和需求，开发者如何更好的理解agent的操作，在利用到coding agent的高开发效率的同时保持对项目的把控，以及尽量消除双方之间认知的mismatch

## 2. 为什么我想做它？

> 在ai辅助项目开发的时候，往往会产生大量的需求文档，连文档本身也成为了需要维护的一部分，整个过程会产生大量的信息冗余和冲突，很多时候ai给出来的更像是一次性的问题解决方案，但是在需要持续开发和维护的复杂系统中，使用体验极其依赖开发者个人的经验和技术能力，否则很难把控整个项目的开发进展，也容易变成说出一个模糊需求后麻木点yes的情况，我希望agent比起bug修改以及专门写代码，能够作为一个长期的项目合作开发者与用户进行合作，提供帮助，整个过程中的文档等设计产物应该是结构清晰并且易于维护，对于双方都有清晰的表意并且能够真实支持后续项目开发与维护的，甚至这个项目和codex，claude code等现有产品并不算是竞争关系，可以做成受支持的额外插件集成到现有工具提供额外的功能

- 整个开发过程中的文档信息有丝分裂导致的认知过载

## 4. 我想象中的一次完整使用过程
### 场景 A：已有项目中增加 Shared Project View

**用户初始输入**

用户说：
> 我想给我的 coding agent 增加一个辅助功能，让用户能通过某种视图清楚理解当前项目结构，并能通过这个视图与 Agent 建立共享的项目认知和语言。

此时需求仍然模糊，例如：
- “项目结构”具体包括什么？
- 用户是想看 architecture、module dependency、execution flow，还是都要？
- 用户是否需要直接编辑这个视图？
- Agent 应该如何使用用户的修正？
- 这个视图只是展示层，还是后续 design / planning 的正式输入？

**阶段 1：需求澄清**

Agent 识别出模糊点，并与用户逐步确认。
用户不需要一次回答所有问题，可以：
- 直接回答
- 选择候选方案
- 将问题标记为 open question
- 要求 Agent 先调研再决定

阶段输出：
- 当前版本的需求定义
- 已确认约束
- open questions
- 暂时假设

**阶段 2：Research**

Agent 根据 open questions 和需求主动提出调研主题，例如：
- 现有 coding agent 如何表示 repository structure？
- Code graph / dependency graph / architecture view 各自解决什么问题？
- Human-AI code comprehension 有哪些已有设计？
- 用户可编辑的 shared representation 有什么常见交互方式？

Agent 向用户展示的不是一篇大报告，而是：
- 关键发现
- 候选方案
- 每个方案的优缺点
- 来源
- 哪些是事实，哪些是 Agent 的判断

用户可以：
- 要求补充某个方向
- 排除某个方案
- 指定来源
- 直接结束调研

**阶段 3：结合现有项目做设计**

Agent 基于：
- 已确认需求
- Research Artifact
- 当前 Project Model

提出集成方案。

用户可以看到：
- 当前系统结构
- 新能力准备挂在哪里
- 哪些模块新增
- 哪些模块修改
- 数据流如何变化
- 用户工作流如何变化
- 哪些设计决策有外部依据
- 哪些地方仍存在不确定性

如果用户认为 Agent 对项目理解有误，可以直接修正 shared project view 或相关 artifact。

阶段输出：
- Design Preview
- architecture / flow change
- impact scope
- risks
- unresolved questions

**阶段 4：形成 Feature Spec**

设计基本确定后，Agent 将其转成可执行的 feature spec，包括：
- functional requirements
- non-functional constraints
- interfaces
- acceptance criteria
- out-of-scope
- expected tests

用户批准后，这个 spec 才成为 implementation 的正式输入。

**阶段 5：实现与验证**

Agent：
- 基于 approved spec 生成 implementation plan
- 在隔离 workspace 中修改代码
- 编写并执行测试
- 检查实现是否偏离 approved design/spec

最后交付：
- 实现代码
- 测试结果
- Semantic Diff
- design/spec → implementation mapping
- 人工验收清单
- known limitations / unresolved issues
